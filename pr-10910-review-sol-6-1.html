What changes

Only the creator replying to a fan can fulfill a pending guarantee

The new shouldFulfillGuaranteedReply helper requires a creator sender, a pending guaranteed reply, and a recipient who is not a creator. The upload flow and send dispatcher use that same check. The three payment payload builders also check it before setting fulfillGuaranteedReply.

A normal fan tip, a paid message, and a message with a tip now carry fulfillGuaranteedReply: false, even when an old pending flag is present. A fan buying a guaranteed reply still keeps the guaranteedReply payment type. Buying a guarantee and fulfilling one remain separate operations.

Fan history cannot restore the creator's pending state

History validation clears isGuaranteedReplyPending for a fan. Incoming guaranteed-reply handling also refuses to set it for a fan. The PR leaves isReplyGuaranteed intact, so the fan's required-tip gate still applies.

A no-op redemption no longer discards the creator's reply

In the message-container callback, a successful response with isRedeemed: false now sends the message and completes its queue entry. The base shows the generic error and never sends the reply in that branch. A redeemed reply still clears the pending flag and shows the wallet confirmation.

A completed payment keeps its success outcome

The checkout callback now opens the existing thank-you popup when redemption returns isRedeemed: false. The payment-success handler already sends the socket message before attempting redemption. The new fallback does not send it again. The existing popup returns the user to their origin when it closes.

HTTP errors still use the existing error handler. The new thank-you path applies to a successful redemption response with nothing redeemed.

Follow-up

A no-op creator redemption still leaves the local pending flag set.

The fallback sends the reply but does not clear incomingGuaranteedReplySid or isGuaranteedReplyPending. Later replies can attempt redemption again, and the pending badge can remain. The base already left that state behind. This PR fixes the blocked send, so I would track the stale-state cleanup separately after confirming what the backend means by isRedeemed: false.

After deployment, check a normal fan tip, a paid message with a tip, and a creator's pending guaranteed reply using test accounts. Confirm the thank-you returns to the conversation, the recipient receives one message, and the creator wallet changes only when the backend redeems the guarantee.
