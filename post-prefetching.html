Development notes

Post prefetching on the white-label homepage

Owner prefetch already started user_by_username from index.html. This change starts page-1 posts and feed ads in that same early script, then holds the feed paint until the live owner GET and checkPrivacy finish. Media is not prefetched. is_private is not baked into the hint.

4 November 2026 branch feature/post-prefetching lab tf-site-4.web.app

What was already shipped

PR 11122 put a tiny per-tenant hint at /assets/owner-prefetch-<user>.json. A script in index.html reads it and starts the owner profile GET before Angular exists. consumeOwnerProfilePrefetch hands that in-flight promise to ProfileComponent once, only if the URL matches. TopFans has no hint, the fetch 404s, nothing starts.

That moved tf:profile-card:visible under 2.5s on a warm host. The first feed row still waited for Angular to boot, then start post/users/post/:gsi4pk. This branch overlaps that GET with the owner GET.

Rules that did not move

  • Do not prefetch media. JSON only.
  • Do not bake privacy into the hint. The live owner GET plus checkPrivacy still decide whether the feed may paint.
  • Cover-page tenants skip posts and ads. isHomepageFeed is false when is_whitelabel_cover_page_published is true.
  • Consume once. URL must match. Another profile on the same tenant must not swallow the owner posts.
  • Do not prefetch every API. Owner, page-1 posts, and the two feed ads. That is the set.

One hint fetch, three GETs

The early script still does one same-origin hint fetch. If the homepage is a feed, it fans that hint into three API GETs. Each slot stores { url, data } so consume can match the path later. encodeURI is on the API URL so a QA baseURL with odd characters does not break the request.

src/index.html

var hintP = fetch('/assets/owner-prefetch.json')
  .then(function (res) { return res.ok ? res.json() : null; })
  .catch(function () { return null; });

window.__tfOwnerProfile = hintP
  .then(function (hint) {
    return fetchJson(hint && (hint.ownerUrl || hint.url));
  })
  .catch(emptyPayload);

window.__tfOwnerPosts = hintP
  .then(function (hint) {
    if (!hint || !hint.isHomepageFeed || !hint.postsUrl) {
      return emptyPayload();
    }
    return fetchJson(hint.postsUrl);
  })
  .catch(emptyPayload);

window.__tfOwnerAds = hintP
  .then(function (hint) {
    if (!hint || !hint.isHomepageFeed || !hint.adsUrl) {
      return emptyPayload();
    }
    return fetchJson(hint.adsUrl);
  })
  .catch(emptyPayload);

White-label generate rewrites the hint path to /assets/owner-prefetch-bonded-wealth.json in that project's index. Slot names live in APP_SHELL_CONSTANTS.OWNER_PREFETCH so the HTML script and AuthService stay on the same strings.

Consume once, URL must match

The early promise is not an Angular cache entry. ProfileComponent still goes through ApiCacheService. If the early slot is present and the absolute URL matches, it uses that payload. Then the slot is cleared. A miss falls back to a normal GET.

src/app/core/auth.service.ts

const consumeEarlyPrefetch = (slot, expectedPath) => {
  const pending = ownerEarly()[slot];
  if (!pending) return null;
  const expectedAbs = expectedOwnerAbsoluteUrl(expectedPath);
  const response$ = from(pending).pipe(
    map((payload) =>
      payload?.url && payload.url === expectedAbs ? payload.data ?? null : null
    )
  );
  ownerEarly()[slot] = undefined;
  return response$;
};

export function consumeOwnerPostsPrefetch(url: string) {
  if (!hasWhiteLabelConfig() || !url) return null;
  return consumeEarlyPrefetch(
    APP_SHELL_CONSTANTS.OWNER_PREFETCH.POSTS,
    url
  );
}

Posts and ads are only consumed when the page is looking at the white-label owner. A deep link to someone else on the same site leaves the owner slots alone so a later visit to / can still use them.

src/app/modules/shared/components/profile/profile.component.ts

getOtherPosts(userId) {
  const postsUrl = APIENDPOINT.otherPosts(userId);
  const prefetched = this.isViewingWhiteLabelOwner()
    ? consumeOwnerPostsPrefetch(postsUrl)
    : null;
  const fresh$ = this.apiCacheService.get(postsUrl, CacheTypes.ALWAYS_FRESH);
  const otherPosts$ = prefetched
    ? prefetched.pipe(switchMap((data) => (data ? of(data) : fresh$)))
    : fresh$;
  // …commitFeedPosts on next
}

Ads use the same consume on post/user/ads?limit=2&ad_format=Feed&from=:gsi4pk&request_from=profile_feed. The Angular ads helper may append device_id. Consume matches the path without that extra query. A miss just does the live GET.

Hold paint until privacy is live

The early posts GET can finish before the owner GET. That is expected. The feed still must not paint a private creator's posts from a public prefetch. commitFeedPosts parks the rows until checkPrivacy has run on the live owner payload.

src/app/modules/shared/components/profile/profile.component.ts

private commitFeedPosts(posts: any[]): void {
  if (!this.feedPrivacyKnown) {
    this.pendingPrefetchPosts = posts;
    return;
  }
  if (this.isPrivate) {
    this.pendingPrefetchPosts = null;
    this.userPosts = [];
    this.isLoader = false;
    return;
  }
  this.pendingPrefetchPosts = null;
  this.userPosts = posts;
  this.isLoader = false;
}

handleUserProfileResponse still calls checkPrivacy. When the homepage is a feed and the prefetch is sitting in pendingPrefetchPosts, privacy flips feedPrivacyKnown and commits in the same turn:

if (this.shouldReusePrefetchedFeed(gsi4pk)) {
  if (this.pendingPrefetchPosts) {
    this.commitFeedPosts(this.pendingPrefetchPosts);
    this.runFeedPostCommitEffects();
  }
}

White-label owner pages no longer skip prefetchFeedIfPossible. The old skip waited for the owner GET before even starting posts. That fight the early script. The owner path now starts startOtherPosts(ownerGsi4pk) immediately and consumes the early promise.

Why the two marks land on the same millisecond

tf:profile-card:visible is scheduled with afterNextRender when the owner profile lands. That same handler calls checkPrivacy, which commits the parked posts and schedules tf:profile:first-card with another afterNextRender. Both callbacks run after one paint. Lighthouse reports whole milliseconds, so they print as the same number.

That is the point of the overlap. On owner-prefetch-only tf-site-2, first-card was typically about 800ms later than the card. Here the posts JSON is already in memory when privacy resolves, so the first row is ready in the same frame as the header.

What the tf-site-4 lab showed

Bonded-wealth QA, desktop Lighthouse, three runs each, cold. Host is tf-site-4.web.app. Marks were copied onto this branch so the lab could see them. LCP is still the prerendered banner. Judge the chain and the app marks, not host TTFB.

AuthProfile GETFeed GETCardFirst cardLCP
logged-out median 118 → 1724 119 → 1515 4311ms 4311ms 3128ms
logged-in median 85 → 2233 85 → 1852 2377ms 2377ms 3259ms

On the 2377ms logged-in run both GETs started at 85ms. Feed finished at 1852ms, profile at 2233ms. The first-card mark still waited for privacy, so it sat at 2377ms even though the posts JSON had been in memory for about 500ms.

Logged-out has no CORS preflight. The early fetch has no Content-Type. Logged-in adds Authorization from fm_user, so the browser sends OPTIONS first. That is why logged-in GET start times in some earlier traces sat near 1.3s even though the script ran at ~266ms. The remasure above caught the actual GETs at 85ms; a later Angular GET with extra headers can still preflight.

Logged-out card marks were noisy across three runs: 4681, 4311, 2006. Same shape every time: profile and feed start together. The median 4311ms is Lighthouse simulated throttling plus a cold host, not a second feed GET. Do not compare that 4311ms to the old warm tf-site-2 1.7–2.3s cluster without saying the host and cache state.
