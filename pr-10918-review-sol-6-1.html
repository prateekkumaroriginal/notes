What the rest of the change does

The account flag becomes a site-specific inbox role

The isCreator getter keeps creators in creator mode on TopFans. On a white-label site, it also requires is_host_owner or an owner identity match. A visiting creator gets fan mode. A non-creator stays in fan mode even if an owner flag is set.

Owner matching already supports the configured owner's gsi4pk and username, compared with the logged-in user's username, referral ID, or gsi4pk. The new role check reuses that existing logic. It agrees with the ownership approach in wls-owner.guard.ts.

The fan role reaches the request and the layout

getInboxTab() returns all for a visiting creator. getChatTypeIndex() uses the fan list slot, and updateActiveTab() chooses General. The three changed template classes also use this contextual role, so the visiting creator gets the fan spacing and tab layout.

The profile callback now filters tab options only for accounts whose stored is_creator is explicitly false. A visiting creator's options remain available internally, while the template hides the creator tab control. This avoids permanently deleting creator options just because the site context temporarily produces fan mode.

The role change also affects guaranteed replies

This getter has consumers outside inbox rendering. For a visiting creator, history handling clears creator pending-reply state and shouldFulfillGuaranteedReply() returns false. That follows the requested fan treatment, but it deserves an account-level smoke check. The change is not limited to hiding Priority and Message Lists.

Broadcasts retain their composer

shouldIncludeMessageValidation() excludes both existing forms of Broadcast and Followers. The inactive gate therefore ignores stale direct-message validation in those threads. A confirmed inactive direct-message recipient loses the footer; a recipient with active: true keeps the previous footer rules.
