Make messages maintainable

Split the page by responsibility. Give each piece one owner for its state, move transport and payment work out of the UI, and preserve the current inbox, history, and send behavior one extraction at a time.

Those 9,154 lines belong to one component. It searches and pages the inbox, selects recipients, fetches history, merges live events, validates DMs, records audio, uploads media, chooses payment paths, manages broadcasts, edits automated messages, opens dialogs, and controls scroll position.

The size is a symptom. The real problem is that changing one job requires understanding all the others. sendMessageApiCall() alone mixes socket payloads, DM credits, tips, guaranteed replies, and payment navigation.

Keep the recent behavior

The current source already has cursor pagination, cancellation on tab or thread changes, an open-thread presence poll, and history responses that can include DM validation. An older plan in notes recommends separate history and permission requests. That recommendation no longer matches this checkout.

  • Keep the existing lazy MESSAGES_ROUTES entry, access guards, and canDeactivateGuard. The route already uses a standalone container. A new NgModule would add work without fixing ownership.
  • Keep ApiCacheService for inbox and presence GETs. History is a POST through ApiCallService, even though it reads data. Preserve groupId, cursor, from, and includeValidation.
  • Keep mergeHistoryWithLiveMessages() and its pending-event buffer when moving history. A socket event can arrive before the first history page returns.
  • Keep server counts as the authority when the socket provides them. Preserve the fallback count updates when counts are absent.
  • Keep message actions disabled while DM validation loads or fails. Readable history and permission status need separate fields even though one request returns both.
  • Keep tenant recipient defaults, owner self-chat checks, delegate permissions, age restrictions, and mobile back navigation. These decisions belong in typed page policy, not repeated template conditions.

The component split

Keep MessageContainerComponent as the route shell. It chooses the active page tab, applies route inputs, handles the mobile layout, and delegates the navigation guard. It should have no upload pipeline, socket-event parsing, or payment branch.

The tree describes ownership. Do not create an empty component for every line in it on day one. Extract the inbox and automated panel as complete units. Split a media variant into another component only when its player, inputs, or lifecycle justify that file.

Keep these components inside src/app/modules/messages/components/. Common buttons, tabs, icons, tables, and skeletons come from src/app/components/. Feature components should not become global shared components just because two message screens use them.

Give state one owner

Moving all 4,746 lines into a MessagesService would leave the same problem. Use small owners with typed state and commands. A page coordinator connects their results. It does not hold another copy of their arrays.

Define contracts before moving state

Reuse Angular's existing input() and output() style. Children receive read-only view models and emit user intents. Do not pass the parent component, a bag of callbacks, or shared mutable arrays into them.

Put pure identity, sorting, day grouping, inbox-count, and merge functions under helpers/. The current older-page merge uses sk || timeStamp, while the live merge uses sk || message_id || uinqueId || id. Characterize both first, then agree on one identity rule. A timestamp alone can collide.

Do not introduce a second global state library for this feature. Use typed local state and the project's existing RxJS patterns for request cancellation. Adopt OnPush in an extracted component after its owner replaces arrays and objects rather than mutating them.

Treat each send as a job

The send path is the highest-risk extraction. A job must capture its conversation and recipient before upload begins. Reading this.sid, this.gsi4pk, or the currently selected tip amount after an asynchronous step can mix two conversations.

  1. Validate the draft and current composer policy. Preserve whitespace checks, media limits, age/delegate restrictions, guaranteed-reply prompts, and minimum-tip rules.
  2. Capture a typed draft snapshot, recipient, tenant owner ID, client message ID, and the relevant validation context.
  3. Upload that job's media and thumbnails. Keep free previews and paid attachments in their recorded order.
  4. Choose the current credit, paid-DM, tip, combined-payment, guaranteed-reply, or broadcast path. Keep the decision in the send coordinator, using a pure eligibility helper where possible.
  5. Apply the result to the original thread and inbox. Match optimistic items by client/server IDs. Clear only the draft that produced the job; a later edit must survive.
  6. Settle progress and guard state on completion, failure, cancellation, or payment handoff according to current behavior.

The code currently marks some socket sends complete immediately after chatService.send(). Preserve that meaning during extraction. Do not rename it "delivered" or invent a server acknowledgement. Payment retry and socket acknowledgement rules need backend confirmation before behavior changes.

Start by moving existing branches intact and testing their results. Refactor payment selection after the job boundary is stable. Do not bundle billing changes with the component split.

Move styles and dialogs with their owners

Angular style encapsulation makes this part easy to miss. Container selectors such as .messages-left .messages-item will stop reaching markup moved into a child. Move those selectors into the child's SCSS in the same change. Check src/assets/scss/_messages.scss too, since global styles also reach the page.

  • Keep only page columns, page tabs, and responsive shell layout in the container SCSS. Inbox rows, bubbles, composer controls, and recorders own their respective styles.
  • Use the six configured theme variables from .guides/color-guide.md in the Angular UI. Use --theme-interactive-link for link text, since the theme color can be a gradient. The palette on this document is only for notes.
  • Create message-specific modal components around AlertModalComponent for inline delete-list, tip-required, and guaranteed-reply dialogs. Keep existing shared dialogs reusable and leave their other consumers intact.
  • Give each dialog typed input data and a result event. The store or coordinator performs the operation after confirmation. Avoid a new universal dialog manager that imports every modal.
  • Group labels, validation messages, media kinds, socket actions, and dialog copy into related const objects. Extract existing hardcoded copy when moving each block. Use as const, not new enums.
  • Use the dynamic form builder when it supports every required field type. Custom attachment ordering, recording, and rich composer behavior can remain dedicated components.
  • Put inbox and thread skeletons under src/app/components/skeleton/. Match their final geometry and theme colors. Reuse the available listing/table skeletons when they fit.

Text input should use Angular bindings. Focus, selection, canvas rendering, and scroll measurement may need a small ViewChild boundary. Remove document-wide queries, manual textarea value writes, and dropdown class manipulation as their UI moves.

Migration order

Each step should leave the application usable. Move one responsibility, remove its old implementation, and verify its behavior before starting the next step. Keep the existing selector and route so callers do not need to change.

1. Capture behavior and establish the types

Record creator, fan, delegate, broadcast, and tenant flows. Add the boundary models and characterize history/live merge, count updates, and send eligibility. Extract pure helpers without changing their behavior. Record the route's loaded chunks as a baseline.

Ready when replayable fixtures explain selection, pagination, counts, validation, and payment branches. Identify the current draft-reset behavior before assigning a new owner.

2. Extract automated messages

Move the table, loading state, list fetch, CRUD callbacks, and delete confirmation into AutomatedMessagesPanelComponent and its store. Keep AutomatedMessageModalComponent. Convert its GET to ApiCacheService with an explicit refresh after writes. Leave its current media editor in place until the shared editor step.

Ready when create, edit, delete, retry, and reopening the panel work without live-thread fields or container callbacks. This is the first implementation slice I would take.

3. Extract inbox and selection

Move the left column and rows, then move cursor/search/count ownership into MessagesInboxStore. Connect selected conversation intents through the page coordinator. Preserve default tabs, deep links, mailing lists, participant edits, and white-label owner selection.

Ready when rapid tab/search changes cannot apply stale results and each row action works on its original conversation. The container no longer owns inbox arrays.

4. Extract thread, history, and live events

Move header and timeline templates with their SCSS. Move history, validation, cancellation, merge helpers, and presence into the thread store. Keep scrolling in the timeline component. Replace the multiple page socket subscriptions with one typed event adapter.

Ready when an A-to-B-to-A switch rejects old responses, a live event survives first-page loading, overlapping pages do not duplicate messages, and prepending history holds the reading position.

5. Extract composer, media, and send jobs

Give the composer its draft store and explicit snapshot submit contract. Move recording and attachment editing, then move the upload/payment/socket flow into the send coordinator. Replace the automated modal's old ImageAudioMessageComponent with the same attachment editor and a separate draft instance. Remove the duplicate logic once both consumers pass.

Ready when switching threads during an upload cannot change its recipient, a newer draft survives an earlier send result, payment paths match existing payloads, and automated-message files never enter the chat draft.

6. Remove the remaining coupling

Move inline dialogs into their owners. Replace broad DOM mutations and scattered subscriptions with owned teardown. Remove obsolete state, imports, duplicated media code, and migrated styles. Enable OnPush only after immutable updates work. Remove the unconditional ngAfterViewChecked() detection loop once the page no longer depends on it.

Ready when the shell handles layout, route intent, policy and navigation only. Optional code can then load on demand if bundle inspection shows a benefit.

Fix teardown at the extraction boundary

Today's container has two destroy subjects and a subscription array. ngOnDestroy() emits destroyV2$, but does not emit destroy$, which several upload/payment/share subscriptions use. It also binds awsRequest.abort without invoking the bound function. Those are concrete cleanup gaps.

Use takeUntilDestroyed() tied to the component-scoped owner's DestroyRef for lifetime cleanup. Keep separate cancellation for replaceable inbox queries, selected threads, presence polls, and individual upload jobs. Component destruction and thread replacement are different events.

  • Cancel the prior presence poll on selection and page exit. Keep browser-only work out of SSR.
  • Stop the microphone, remove listeners, revoke owned object URLs, and call the actual upload abort operation when its owner cancels.
  • Protect writes with a selection generation or request identity. Checking only the conversation ID is insufficient for A-to-B-to-A navigation.
  • Keep the shell's navigation guard connected to active send jobs. The current guard checks the queue, not unsent text. Adding a draft warning would be a separate product change.

What completion looks like

  • The shell has no API calls, raw socket parsing, media upload loops, payment branches, or direct access to child draft fields.
  • Inbox, thread, draft, send queue, and automated messages each have one authoritative state owner. Their public contracts use named types instead of any.
  • A row or bubble consumes a view model and emits intents. It cannot mutate the parent's arrays.
  • Direct and automated messages use the same attachment editor with independent drafts. Legacy duplicate media code is removed.
  • New modal components use AlertModalComponent. Migrated copy uses grouped constants. Every extracted component has its own SCSS and verified tenant theme.
  • The regression cases above pass on the main project and a generated tenant. No unconditional view-check detection loop or document-wide UI mutations remain in the messages feature.

I would start with automated messages, then inbox ownership. Those changes establish the component and state pattern before touching the upload and payment path. File count is not the success measure. Being able to change inbox search without reading send-credit logic is.
