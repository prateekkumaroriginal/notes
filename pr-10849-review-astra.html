What changes

Zero components are deleted. The PR removes 53 eager component imports and their repeated template branches from MarketingPageFullPreviewComponent. A new registry loads those same components through dynamic imports. The header stays statically imported, so its projected user menu keeps the existing template structure.

The 345 deleted lines mainly belong to imports and repeated markup. This is different from PR 10845's unused-component deletion. The layout files and their styles stay in the application.

Here, visible means isVisible !== false. All enabled sections load together, including sections below the fold. Scrolling does not trigger the imports.

Code review

Every old layout has a destination

I checked all 54 old switch cases against the new registry. There are 53 dynamic loaders and one static header. Each loader resolves to the expected exported component and selector.

The input audit compared 53 layouts across eight combinations of CMS mode, desktop or mobile preview, and logo synchronization. All 424 comparisons match the old template bindings, including branding inputs and special layout flags.

Server rendering waits for the imports

The loader registers work with Angular PendingTasks and releases it in a finally block. That keeps server rendering from completing before the layout imports settle. After loading, markForCheck updates this OnPush component.

A generation counter discards results from an older request or a destroyed preview. Changes to CMS mode, viewport, logo synchronization and branding rebuild the input objects. The header and welcome-video template remain static.

One failure-handling improvement remains

The imports use Promise.all. If one required chunk fails, the component does not publish any results from that batch, and there is no local error message or retry. PendingTasks still gets released.

I would add a retry or fallback in a follow-up. I did not reproduce a layout-import failure in the successful page checks, and this is not a blocker for this change.
