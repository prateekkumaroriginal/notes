The number that matters

Production cannot report tf:profile-card:visible. The closest proxy is when user_by_username finishes. On the lab, the mark is that finish plus one afterNextRender, about 80ms later.

Production starts the profile GET after bootstrap, then waits on OPTIONS. Best case in this pair, the body is done at 5.7s. The lab starts the same URL at 118ms from the HTML script and paints the card at 2.3s.

Same API, two bodies

The QA API already knows Origin: https://www.bondedwealth.com. That origin gets the slim homepage view from the view cuts. Origin: https://tf-site-2.web.app is not on that list, so the lab gets the fat payload. I confirmed this with curl, not only Lighthouse.

Origin bondedwealth.comOrigin tf-site-2.web.app
Bytes 1608 15453
Name, bio, banner, location flag Present Present
subscriptions Missing About 12 KB of the body

The lab beat 2.5s while downloading the fat body. Production already has the cheap body and still cannot start the GET until Angular is up. Shipping the overlap to production should land under the lab number, not above it, because the API work is already live for that origin.

What I would not claim

  • That Firebase is faster than S3 in production. TTFB and CSS transfer are host noise. The card win is the request schedule.
  • That production is already under 2.5s. It has no mark, and the GET that feeds the card still starts after 4s on a warm edge.
  • That LCP improved. It did not. Same banner, ~3.4s both sides.
  • A logged-in comparison. QA login creds are not a production session, and production here is already talking to the QA API.
