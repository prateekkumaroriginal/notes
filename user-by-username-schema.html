Development notes

user_by_username response cuts

Frontend contract for GET api/user_by_username/:name. Guest fat payload today is 34.6KB. 25.7KB of that is subscriptions[]. Do not slim the bare URL. Other screens still call it.

same path, four query cuts profile first GET drops the 26KB plan list

Rule

Same path, different query. ?view=profile|plans|identity|events. Leave api/user_by_username/:name with no query as the current fat response until every caller is switched.

Forum already uses ?basic=true. That cut is not enough for the profile card: no viewer fields, no events, VIP, or portfolio, and it still ships category.

Four cuts

viewForvs fat
profile Profile first paint. Card, feed gate, on-screen buttons. No pop-in. Less. No subscriptions[].
plans Store, courses, lessons, livestream, newsletter, portfolio, wallet, share preview, View Plans modal. Less data. Same plan list, slimmer plan objects.

events Event listing, ticket preview. Less data. Keep eventDetails + email.

Other screens need less of data and more of one envelope slice. They do not need the profile card schema plus extra user fields.

  • Gate View Plans on has_subscriptions, not userSubscriptionList.length.
  • Move api/subscribe/user to the plans click.
  • Leave every other APIENDPOINT.user caller on the fat URL until its cut exists.
