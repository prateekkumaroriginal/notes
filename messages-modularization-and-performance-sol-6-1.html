Break up the messages page and make it faster

Ship the loading fix first. Then split the page around inbox, thread, composer, and automated messages. Use Angular 21 patterns in each extracted component, with separate changes for app-wide migrations.

Recommendation by sol-6-1, 1 Oct 2026. Audited frontend b4eecd4a60 and the current source against the Opus speed investigation. This document proposes the work. It does not implement or benchmark it.

Why I would start with the loading fix

MessageContainerComponent has 4,283 lines of TypeScript, 3,118 lines of HTML, and 1,218 lines of SCSS. Splitting it will make changes easier to review. File count alone will not remove a network wait or keep an emoji library out of the first download.

The speed report identifies a smaller change that can ship before the extraction. I checked these findings in the current source:

  • getUserEmail() waits 1,000 ms before validation, even when the selected participant is available.
  • getUserChatMessage() and checkNewUserValidation() both emit to userValidationCancel$. Parallelizing them without changing cancellation would cancel one request.
  • msgrightLoader hides history and the composer together. The inbox request also clears it in its completion handler.
  • scrollToBottom() waits another 500 ms. ngAfterViewChecked() calls detectChanges() on every view check.
  • The container eagerly imports the picker, audio player, table, and share dialogs. receiveMessage() also refetches the inbox.

The first change should establish a reliable selected-thread flow. That gives the extraction a clearer contract. A full component rewrite first would leave users waiting while we move the same problems between files.

The report's timing and bundle estimates are hypotheses from an earlier build. Its author had no authenticated timing session. I confirmed the source patterns above, not the proposed 0.6 s load time or 450 KB saving.

The proposed final component tree

Keep MessageContainerComponent as the route entry. It owns page layout, feature tabs, route integration, and the existing navigation guard. The children below are proposed components unless marked as existing. Shared buttons, tabs, skeletons, and icons are omitted from the tree.

Dialogs sit outside this permanent tree. A lightweight MessagesDialogService loads the existing new-message, participants, price, share, image-preview, and video dialogs when requested. Extract the container's inline delete and tip/guaranteed-reply dialogs into dedicated components based on AlertModalComponent.

Do not make a component for every icon or conditional branch. The useful boundary is a part with its own behavior, a repeated renderer, or an expensive dependency. The first extraction can be coarser than this tree.

There is already an ImageAudioMessageComponent used by the automated-message editor. It duplicates attachment and recording behavior and owns mutable state. Keep it working during the first extraction. Share the new attachment and recording pieces after both consumers have a compatible draft contract.

Moving the template is only half the work

The container should stop owning API calls, upload steps, payment branches, and message formatting. Copying all 4,283 TS lines into a single service would leave the maintenance problem intact.

Keep page-session state with the container and draft state with its owning composer. Do not assume a route provider is destroyed on every navigation; define session reset and subscription cleanup explicitly. Stateless adapters can be root singletons. A later root cache should retain only bounded, intentional data and clear it on account or tenant changes.

Components receive typed, read-only models and emit actions such as select, retry, send, remove attachment, and unlock. Do not pass the parent component to a child or let children mutate its arrays. Keep temporary forwarding methods while extracting, then remove them.

The thread selection includes groupId, participant ID, conversation kind, and account/tenant context. History and permission streams independently cancel old selections. Late responses and their cleanup must check the selection generation before updating state. A shared forkJoin would wait for both responses and hide the benefit of early history.

Normalize API responses once into message and conversation models. Give an optimistic send a stable render ID that survives the server response; preserve the existing uinqueId matching until that adapter is tested. Replacing an optimistic ID with a server ID can otherwise recreate the row and interrupt media.

Where I would adjust the speed report

Accept the loading changes, keep selection rules explicit

Start history and permissions together when the participant is known. Handle direct links, new groups, broadcasts, and white-label owner targeting separately. Clear the previous thread's permission state immediately. Unknown or failed validation must never fall through to free sending.

Pair code splitting with extraction

A smaller component remains eager if the shell still imports it eagerly. Use deferred standalone wrappers for the picker, players, and automation panel, and dynamic imports for dialogs. A child class referenced outside its defer block or in a component query can remain eager. Making a query optional does not fix that reference. Verify the actual chunks. Angular documents these defer conditions.

Move scrolling to the timeline, then remove timing guesses

The timeline owns scrolling. Use a browser render callback such as afterNextRender to wait for the view. Give media reserved dimensions and account for later media sizing. Keep the reader's position when older history arrives or a new message arrives while they read above the bottom. Angular's render callback guidance explains when callbacks run and why SSR needs separate handling.

Defer cache and backend work until the frontend contracts settle

The proposed paginated inbox, thread bootstrap, and websocket row deltas are sensible API discussions. They do not block the first loading fix or component split. Keep the full-inbox fallback until event payloads can maintain classification and unread totals. Decide on virtualization after profiling large inboxes. Variable-height message media makes timeline virtualization a separate task.

Early prefetch must not pull the whole messages dependency tree into the app shell. Keep any prefetch adapter small and browser-only. Private cache keys need account, tenant, permission context, tab, search and conversation identity. The current GET cache keys come from the endpoint, so do not assume they provide that isolation.

Angular 21 source changes belong in the extraction

package.json already targets Angular 21.2.x and TypeScript 5.9. The messages route already loads lazily, the container is standalone, its template uses @if and @for, and its queries use viewChild(). A new package-upgrade phase is unnecessary for this checkout. Most remaining work is state ownership and update behavior.

Signals and RxJS have different jobs here. Signals expose current state to the template. RxJS handles asynchronous selection, cancellation, and events. There is no need to replace a working request stream just to make the code look newer.

These choices follow Angular's guidance on signal inputs, outputs, OnPush, and subscription cleanup. Angular 21 defaults to zoneless, but this app opts into Zone. Evaluate an app-wide switch later, after the websocket, modal, upload, and SSR updates have explicit notifications. See Angular's zoneless migration guide.

Put labels in grouped as const files and keep endpoint and tenant URLs in existing configuration. Do not copy the current hardcoded labels or document-wide element lookups into the new components.

What each stage must prove

  • Measure cold route entry separately from warm return. Record route activation, inbox paint, history paint and composer enabled. Compare production builds on the same network and device profile, with repeated runs and p75/p95 results.
  • Check fast thread switches, overlapping searches, incoming messages during loading, empty history, failed validation, and retries. History remains readable; stale permission state never enables an action.
  • Preserve Priority / General / Bulk default selection, unread totals, direct links through ?user=, tip-back id, and history.state. Test creator, fan and delegate access.
  • Cover paid DM, remaining free credits, tip-required and guaranteed replies, locked media, shared items, mailing lists, recording, failed uploads and optimistic sends. Keep canDeactivate() attached to the queue owner; the existing guard blocks navigation when queued messages remain.
  • Compare main TopFans and one generated white-label project, including hidden inbox, owner targeting, WLSAllowDMs, tenant themes and mobile bridge file picking. Check SSR/hydration without browser globals running on the server.
  • Use --stats-json and the browser network trace to verify optional libraries load only when used. Check typing and scrolling after removing the repeated detectChanges() hook.

Build with the required --max_old_space_size=10048. npm run build-dev already supplies it. Use equivalent memory settings for production and white-label validation. Keep data-ordering and cancellation tests where behavior changes; component-count tests do not tell us whether chat still works.

The app-shell bundle cost reported by Opus can still limit cold entry after the messages route improves. Measure it separately. Do not promise a total page-load target from component-start estimates.

Answers to the four questions

  1. Which should we do first, breakdown or speedup?

    The small thread-loading speedup first, after a baseline. Fix cancellation and independent history/permission state, then remove the participant timer. Component extraction follows. The broader speed work continues through and after that extraction.

  2. What will the final message component tree look like?

    A thin MessageContainer with inbox, thread, composer, and an optional automated panel. The thread contains a header and timeline, the timeline renders message items, and the composer owns draft UI. Optional players, picker, recorder, and dialogs load when needed. The full tree and non-UI owners are above.

  3. Should we do both simultaneously or one by one?

    One effort with sequential, independently testable changes. Pair each component extraction with the optimization its boundary enables. Avoid a single rewrite PR and avoid concurrent edits to the monolith. Backend investigation can continue alongside the frontend work.

  4. Should Angular 21 source modernization happen now, before, or later?

    Do local modernization during extraction. Angular 21 packages and several syntax migrations are already in place. Write each new component with typed signal contracts, OnPush, stable tracking and owned cleanup. Keep zoneless, app-wide migrations and library replacements for separate work after the messages changes are stable.
