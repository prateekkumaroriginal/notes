How a page loads layouts

loadVisibleLayoutComponents

Visible section ids are deduped. The header is skipped. Ids that already have a class are skipped. The rest import together. PendingTasks stays open until that batch finishes, including when the import throws, so server rendering does not wait forever. After a successful batch the classes are stored and markForCheck runs. The preview is OnPush.

A newer resolve, or ngOnDestroy, bumps layoutLoadGeneration. A stale batch does not write classes. Viewport, branding, and preview-mode changes rebuild layoutInputs without importing again. NgComponentOutlet applies those inputs on the existing component.

Angular's ViewContainerRef.createComponent looks up a server-rendered view by component id. The pending task is what keeps the app unstable until the class is assigned and change detection is scheduled, which is the window that lookup needs. I did not watch a browser for a hydration error.

One sharp edge. The batch is Promise.all. If one chunk rejects, none of that batch is stored, and the void call leaves an unhandled rejection. A missing chunk should fail one section. I would not hold the merge for it.
