Socket tab movement is deferred

message-container.component.ts, lines 2854 to 2874

The user has accepted this as follow-up work. It does not block this merge.

The handler first searches the tab named by the socket event. If it cannot find the row there, it searches every loaded tab and updates whichever copy it finds. It never moves that row to the server's tab and does not refresh after finding it in a different tab.

  1. Load a conversation in General.
  2. Deliver an event for that conversation with tab=featured.
  3. The handler finds the General copy and updates it there. Priority still has no copy.

The fixture ended with zero Priority rows and one General row. This matters whenever the server changes membership, such as a conversation moving into Priority. The event's server tab and its counts can disagree with the visible list until another inbox request repairs it.

Handle a tab mismatch explicitly. Remove the stale copy and refresh the relevant tab, or move the row with the server's membership and ordering. Do not reuse the old tab index as the destination.

Verify the fan count response before treating it as a defect

message-container.component.ts, lines 3898 to 3917

Fans have one combined inbox and no creator tab badges. The component stores tab=all at index 2, then uses that index to subtract read counts from General. This matters to the sidebar total only if the fan API distributes unread counts across multiple categories.

The fixture supplied Featured 3, General 2, and Broadcast 0. Reading a conversation with 3 Featured unread messages left the sidebar at 3 instead of 2. That proves the calculation under those inputs. It does not prove that the live fan API returns those inputs.

If the fan API aggregates all unread messages into General, this case does not apply. I have not verified a live fan response and should not have classified this as a confirmed merge blocker. Check the backend contract during the later investigation.
