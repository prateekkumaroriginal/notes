Human QA checklist

1. Record the test setup

Record the deployed build, browser, device, viewport, role and page URL. Start with tf-prefetch-4 for the final source snapshot. Use a TopFans build as well as bonded-wealth QA to cover branches hidden on tenant sites.

Expected. Setup recorded. Mark a hidden or unauthorized branch N/A with the reason in your report.

2. Use a fresh app session for each target

Open DevTools Network, preserve the log and filter to JS. Clear site data or use a fresh private session. Check Disable cache and reload a source page that has not loaded the destination. Check for an active service worker if requests still come from cache.

Expected. The destination code is cold before the trigger. A reload also clears the service's in-memory started set. Disable cache alone does not unload modules already imported by the running app.

3. Separate view from intent

Keep the pointer away from the target before reload. For a view-enabled binding, wait at least a few seconds without touching it. For intent-only bindings, wait, then hover the target.

Expected. View-enabled targets may request code while idle. Intent-only targets wait for mouseenter, focusin or pointerdown. Other links to the same chunk can load it first, so isolate the target before judging it.

4. Check a sidebar entry into Wallet

With a logged-in account and a visible sidebar, cold-load a non-Wallet page. Wait for idle requests, then click Wallet. Repeat in a new session with effectiveType reporting 2g.

Expected. The enabled session fetches Wallet code before the click. The constrained session skips the speculative download and navigation still succeeds. The earlier 13-to-zero result is a reference, not a fixed chunk-count requirement.

5. Check header and user menu

Test New post and Messages. Open the avatar menu on desktop, then at phone width. Test desktop Edit Preferences and the mobile Settings list. Hover the legal links separately.

Expected. Settings code can load when the visible menu renders. Legal links use intent. Each click still opens its original destination. Test owner, fan and guest branches where available.

6. Check Features and Compare dropdowns

Cold-load a public TopFans page, then open Features. In another fresh session open Compare. Keep the pointer off the item grid until after opening. Include a marketing-pro destination.

Expected. Opening a panel makes its view-enabled items eligible for idle preloading. Marketing, comparison and marketing-pro need their respective component code. The dropdown click still closes the panel and opens the correct page.

7. Check profile chrome on both site types

Open your own TopFans profile at desktop and phone widths. Repeat on the white-label QA site. Test sign-in, edit profile, profile actions, event and loyalty links that your role can see.

Expected. Visible targets preload with their listed trigger. Some own-profile header actions are hidden on white-label sites. Record those as N/A for that site and test them on TopFans.

8. Check all 12 Monetize tabs

As the owner, start on one Monetize tab with the pointer outside the tab bar. Wait, then hover or focus a different tab before clicking. Repeat for each tab from a cold session when needed.

Expected. A different tab starts its lazy-code request on intent. Merely opening Monetize should not make these bindings preload every tab. Existing/shared chunks may produce no new request.

9. Check create and add buttons

Test the add/create variants in subscription plans, newsletters, merchandise, NFTs, downloadables, courses, experiences, VIP offers, event calendar and discount codes. Include populated and empty-state layouts shown in the inventory.

Expected. The form code starts on intent. The form itself opens only on click, with the same route and state as before. Merely rendering a list does not preload all its forms.

10. Retest the leaf-route bug

On VIP offers, cold-load the list and hover Add offer. Repeat with the courses list and Create course. Then click each button.

Expected. The add/create form's code loads, not just the list code that is already open. No route mismatch or missing-form error appears after the click.

11. Test direct-entry back and edit links

Open a Monetize create/edit page directly by URL in a fresh session. Observe its view-enabled back link. Separately open a list directly, avoid its add button and hover an edit link.

Expected. The back link can preload its list even without a preceding list visit. Edit uses intent and opens the same record. Do not assume the add button has already covered it.

12. Check ordinary post cards and downloadables

Find the same shared post-card component in a home feed and a forum layout. Hover an ordinary post card, then click. In a fresh session repeat for a downloadable. Test avatar/name separately.

Expected. Ordinary posts preload post-detail code. Downloadables target Dashboard. Avatar/name target the profile. Hover does not fetch the destination's page data through this preloader or change the route.

13. Check table targets across every configured column

Use the 19 column configs below. Find a row with a valid target and hover its clickable cell, image or action. Test a missing-ID row and non-clickable title/description flags where those data states are available.

Expected. Configured targets load on intent. Missing targets and disabled title/description areas do nothing. Modal-only or unconfigured columns do not gain unrelated preloads. A cell's original callback still runs on click.

14. Check handlers with side effects

Test the creator-requirements checkbox, login dialogs, ticket edit/redeem, newsletters, checkout actions, link-in-bio links and carousel targets. Use the inventory's exact elements and context.

Expected. Hover/focus/press downloads code only. It does not submit a form, create a record, dismiss a modal, bypass a checkbox or open a login dialog. The click keeps its previous behavior.

15. Check live-stream and Edit post limits

As the owner, hover a go-live opener before opening the modal. Test an Edit post item from a directly opened post. Check tenant visibility before looking for the reels Edit post action.

Expected. Go-live can preload Dashboard before the modal choice. A destination outside Dashboard may still need code. Edit post can show no new requests because New post already loaded Dashboard. Hidden actions are N/A, not failures.

16. Check keyboard intent

Use Tab to reach a native link or button without hovering it. Wait before Enter or Space. Also inspect custom component hosts and clickable divs for their existing keyboard access.

Expected. Focusable elements trigger focusin before activation. Preloading does not add tabindex or keyboard semantics to a non-focusable host. Report an inaccessible control separately; do not count a mouse test as keyboard coverage.

17. Check touch and pointer intent

On a real phone or touch-capable browser, cold-load the source and tap an intent-only target. Compare request timing to pointerdown and click with Network or a performance recording.

Expected. The preload starts on pointerdown when a target is available. A quick tap may navigate before the download finishes. No claim of zero post-click requests is required for that tap.

18. Check network opt-outs

In DevTools inspect navigator.connection.saveData and navigator.connection.effectiveType. Test a browser/device that reports Save-Data or 2g/slow-2g, then restore the normal connection and reload. Do not assume a throttling preset changes effectiveType.

Expected. No speculative route-code requests from this feature on the constrained session. Normal click navigation still loads code. Browsers without Network Information hints follow the normal path.

19. Check retries and repeated targets

Use a cold target, block or fail its chunk request, trigger intent and confirm the failure. Unblock and trigger again before clicking. Then hover another URL that shares the same imported component.

Expected. A rejected async load permits another trigger to retry. Successful repeated exact URLs do not restart service work. Different URLs can call the same loader, while module caching normally avoids another download.

20. Check data, navigation and rendering regressions

Watch Fetch/XHR and console while hovering. Compare with an idle control recording to identify background polling or the separate homepage prefetch. Visit public and authenticated routes directly, then navigate to the preloaded destinations.

Expected. No destination data request is initiated by RoutePreloadService. No route change until activation, no guard bypass, no new console or hydration error, and correct destination, query, fragment and record after click. Existing lazy CSS and data may still load on navigation.

21. Complete the binding inventory

For each applicable entry below, record Pass, Fail or N/A. Search by component path, target or handler. Test loops with representative data and each conditional destination branch. Download a report at the end.

Expected. Every source binding and all 19 populated table configs have a result. For N/A entries, record the role, site or missing test data that prevented exercise. A passed source-level check is not a browser pass.
