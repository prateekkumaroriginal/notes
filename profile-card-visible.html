Development notes

How the profile card got under 2.5s

The KPI is tf:profile-card:visible. That is the moment the white-label profile header is on screen. Banner slot, logo, name, location, nav pills, bio, subscribe button. Not the feed. Not the banner image finishing. On a warm Firebase host the mark dropped from about 3.1s to the 1.7s to 2.3s range.

3 November 2026 branch feature/profile-performance-measurement lab tf-site-2.web.app

What we were actually timing

Lighthouse LCP is the banner image. Fine as a Core Web Vital. Useless as a "can I see who this creator is" number. The profile card mark fires in handleUserProfileResponse after setUserProfileWithBadges, then one afterNextRender. If the GET has not come back, the mark cannot fire.

src/app/utils/profile-perf-marks.ts

export const PROFILE_PERF_MARKS = {
  BOOTSTRAP: 'tf:bootstrap',
  HYDRATION: 'tf:hydration',
  LANDING_FEED: 'tf:landing:decision:feed',
  PROFILE_CARD_VISIBLE: 'tf:profile-card:visible',
  FIRST_CARD: 'tf:profile:first-card'
} as const;

tf:profile:first-card is a different clock. It waits for the first feed row. We left it alone. The loop stopped when the card mark went under 2.5s, not when the feed did.

Why it sat at 3 seconds

On a white-label homepage the HTML is prerendered. The profile payload is not in that HTML. The browser still had to boot Angular, read wls-config.json, decide cover vs feed, construct ProfileComponent, then start api/user_by_username/.... The GET was a CORS request too, because every GET left the office with Content-Type: application/json. Browsers treat that as non-simple, so they send OPTIONS first.

Bootstrap itself was around 1.1s on a warm host. The card waited another two seconds for a request that could have started with the HTML.

The move that actually paid

Start the owner profile GET from index.html, before Angular exists. Hide the URL in a tiny per-build hint file so the shared shell does not hardcode a tenant. When ProfileComponent asks for the same path, hand it the in-flight promise instead of opening a second GET.

On a warm host the profile GET now starts around 50 to 130ms and finishes around 1.7 to 2.2s. Bootstrap still lands near 1.0 to 1.6s. The card no longer waits for bootstrap to begin the request. It only waits for the request to finish and for one render.

Early fetch in the HTML

src/index.html

window.__tfOwnerProfile = fetch('/assets/owner-prefetch.json')
  .then(function (res) { return res.ok ? res.json() : null; })
  .then(function (hint) {
    if (!hint || !hint.url) return null;
    var headers = {};
    try {
      var raw = localStorage.getItem('fm_user');
      var token = raw && JSON.parse(raw).fm_user;
      if (token) headers.Authorization = token;
    } catch (e) {}
    return fetch(hint.url, { headers: headers }).then(function (res) {
      return res.ok ? res.json() : null;
    });
  })
  .catch(function () { return null; });

scripts/write-owner-prefetch.mjs reads the tenant env file and writes src/assets/owner-prefetch.json. That file is gitignored. A white-label QA build for bonded-wealth gets a hint like api/user_by_username/<owner>?wlsOwner=true against the QA baseURL. TopFans has no hint file, the fetch 404s, the promise resolves null, and nothing tenant-specific leaks onto topfan.com.

This is a raw fetch on purpose. ApiCacheService does not exist yet. The Angular path still goes through the cache service. The HTML script only starts the network work early.

Hand the response to ProfileComponent

prefetchWhiteLabelOwnerProfile is a second APP_INITIALIZER. Browser plus white-label only. It preconnects the API origin, then starts the same GET through ApiCacheService with CacheTypes.ALWAYS_FRESH. That covers the case where the HTML fetch missed or came back empty.

getUserProfile used to always open a new REFRESH_EVERY_N GET. Now it asks consumeOwnerProfilePrefetch(profileUrl) first.

src/app/modules/shared/components/profile/profile.component.ts

const profileUrl = this.userByUsernameUrl(userId);
const prefetched = consumeOwnerProfilePrefetch(profileUrl);
const fresh$ = this.apiCacheService.get(profileUrl, CacheTypes.ALWAYS_FRESH);
(prefetched
  ? prefetched.pipe(switchMap((data) => (data ? of(data) : fresh$)))
  : fresh$)

Consume is URL-gated. The early promise is the owner. A deep link to someone else on the same tenant must not swallow that payload. If the URL does not match APIENDPOINT.userProfileView(owner, wlsOwner), consume returns null and the normal GET runs.

ALWAYS_FRESH is the cache type because the first paint is what we are buying. A 30-second stale profile from REFRESH_EVERY_N would hide a miss and still not help a cold lab run.

Stop sending Content-Type on GET

src/app/core/http.service.ts

if (type === Application.TYPE_GET) {
  const newOptions = {
    ...httpOptions,
    ...(options || {}),
    headers:
      (options as { headers?: HttpHeaders })?.headers ??
      httpOptions.headers.delete('Content-Type')
  };

A GET with a JSON content type is not a simple request. The browser pauses for OPTIONS. On the old logged-out trace that preflight ate 800ms after bootstrap. The early fetch in index.html never set Content-Type, so it was already simple. This change makes the Angular GET simple too, for every caller that does not pass its own headers. POSTs are untouched.

What this did not fix

  • LCP is still the banner image, around 2.9 to 3.1s.
  • CLS is still 0.564 from the sidebar ad skeleton.
  • tf:profile:first-card is still 2.8 to 3.8s. The feed GET still starts after the profile GET.
  • A cold Firebase edge still costs a second or more of TTFB and delayed JS. Do not read that as a regression in the card path.
  • The hardcoded TopFan WebSite JSON-LD came out of shared index.html. It named topfan.com on every tenant. SeoService still injects structured data per page.
