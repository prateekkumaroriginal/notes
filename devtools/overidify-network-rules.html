How Overidify builds a Network Rule in DevTools

Start with a Fetch/XHR request that Chrome has already recorded. Select it, edit the response, and save. Overidify fills in the request details and creates a Network Rule.

Implementation at commit 5a0ef7f. Written on 28 October 2026.

The change removes the setup form

The original Network Rule editor asks for a name, website domain, request URL, method, response body, status, and headers. Most of these values already exist in DevTools. Entering them again makes a small response change feel like a separate task.

The new panel asks you to change the response. It reads the other values from the captured request and the inspected browser tab. The saved rule uses the existing storage, matching, and interception code.

Network Rule
A saved rule that returns a mock response for a request target within a website scope.
Request target
The API URL and HTTP method that the rule matches.
Website scope
The website in the address bar. This decides which website tabs can use the rule.
Mock response
The response body, status code, and complete set of response headers that the page receives.
Activation
The background worker sends the saved rules to matching website tabs. A saved rule can still need a page reload before it takes effect.

The full flow

  1. Chrome records the request

    The DevTools network API supplies a request handle. Overidify keeps only supported HTTP or HTTPS Fetch/XHR calls.

  2. You select the request

    The panel reads its response body. It also gets the inspected tab's URL from Chrome.

  3. Overidify builds a draft

    The request supplies the URL, method, status, headers, and rule name. The tab supplies the website scope.

  4. You edit and save

    The form validates the draft and saves it as a Network Rule. The background worker then starts activation.

  5. The next matching call receives the mock

    The page interceptor checks the saved rule. In bypass-server mode, it returns the mock without calling the API.

Chrome loads the panel

manifest.config.ts declares devtools.html as the extension's devtools_page. Chrome loads this page when DevTools opens. Its script, src/devtools/register.ts, creates a panel named Overidify.

chrome.devtools.panels.create(
  'Overidify',
  'icons/icon-32.png',
  'devtools-panel.html',
  panel => {
    panel.onShown.addListener(panelWindow => {
      panelWindow.dispatchEvent(
        new Event('overidify-devtools-shown')
      )
    })
  }
)

devtools-panel.html loads the React entry point. Vite has a separate build entry for this HTML file. The panel listens for the shown event and refreshes its request history when you return from another DevTools tab.

Capture handles first, read bodies later

observeDevtoolsRequests() has two inputs. getHAR() reads requests already known to DevTools. onRequestFinished supplies new completed requests. HAR is Chrome's HTTP Archive representation of a request and response.

The picker checks Chrome's _resourceType field. It accepts fetch and xhr. A script or image that returns JSON still stays out of the picker. The request must also have a valid HTTP or HTTPS URL and a supported method.

The observer keeps the latest 200 requests in memory. It stores the request handles, not all response bodies. Only selecting a request calls getContent().

Merge history with live events

A request can arrive through a live event and also appear in a history refresh. The observer compares its start time, method, and URL, then counts matching occurrences. It skips entries already represented in the live list.

Each capture still gets a separate sequence ID. Two calls to the same URL in the same millisecond remain separate rows. A timestamp alone would incorrectly merge them.

Reject stale history callbacks

A navigation or Clear action changes the capture generation. Each refresh also gets a version number. A callback from an old generation or an older refresh cannot restore stale entries. Navigation clears the selected request and starts a fresh history read.

Build the Network Rule from the capture

CapturedResponseEditor asks Chrome for the inspected tab. It passes that tab's URL and the selected request to draftFromDevtoolsRequest(). If you select another request before the read finishes, the old editor cannot apply its late result.

For example, the address bar is http://localhost:4200/messages. The captured call is GET https://api.example.test/v1/chats?tab=featured. The draft has these values:

{
  name: 'GET /v1/chats',
  url: 'localhost:4200',
  requestUrl: 'https://api.example.test/v1/chats?tab=featured',
  method: 'GET',
  enabled: true,
  mode: 'bypass',
  status: 200,
  headers: [{ key: 'Content-Type', value: 'application/json' }],
  body: '{"chats":[]}'
}

url holds the website scope. requestUrl holds the request target. The API host does not become the website scope. A captured status from 200 to 599 is retained. Otherwise the draft starts at 200.

Read text without changing it

The converter preserves plain response text. It decodes base64 as UTF-8 and rejects content that cannot be decoded as text. It accepts text response types, including JSON and XML. It rejects binary response types. Empty text is valid.

Invalid JSON produces a warning when the Content-Type is JSON. It does not block saving. A mock can intentionally return invalid JSON to exercise the application's failure handling.

Copy application headers

The converter removes Set-Cookie, Set-Cookie2, Content-Length, Content-Encoding, Transfer-Encoding, Connection, Keep-Alive, Proxy-Connection, Trailer, Upgrade, and pseudo-headers that start with a colon.

Chrome has already decoded the body. The original transport headers can describe different bytes. Mock response headers also cannot set browser cookies. If Content-Type is missing, the converter uses the captured MIME type.

Save first, then confirm activation

The response form exposes the body and status code. It validates the draft with NetworkRuleDraftSchema. The full Network Rule editor remains available through Edit all settings after saving.

The form creates one UUID for its Network Rule. saveDevtoolsOverride() reuses that UUID on later saves and retries. If the rule exists, the function updates it. Otherwise it appends a new rule.

// These are two separate operations.
saveDevtoolsOverride(id, draft)
  → updateNetworkRules(update)
  → chrome.storage.local
  → sync-network-rules
  → background worker
  → matching website tabs

updateNetworkRules() uses a browser lock while it reads and writes the rule collection. A settings-page edit and a panel save can run at the same time without overwriting each other's collection changes.

After the storage write, the extension asks the background worker to activate the rules. The worker finds website tabs with the shared domain matcher. It sends their rules through the isolated content-script bridge to the interceptor in the page's main JavaScript world.

The activation result includes tab IDs that need a reload. The panel checks the inspected tab's ID and shows a Reload page button when needed.

An activation error can occur after the rule has been saved. Retrying the save uses the same UUID, so it does not create a second rule. Capture, save, and retry do not replay the original API request.

The existing interceptor delivers the mock

The DevTools panel prepares the Network Rule. The existing page interceptor applies it. network-page.js installs at document_start and wraps page and iframe Fetch/XHR calls.

Website eligibility uses matchesPageDomain(), the same matcher used by Header Rules, Switch Rules, and the popup. Request matching then compares the method and normalized API URL. It ignores URL fragments and query-parameter order. It preserves parameter values, repeated parameters, and the path. The later enabled matching Network Rule wins.

Bypass-server mode
This is the panel's default. The interceptor returns a synthetic response to the page. It does not make the target server call. Trigger the request again in your app to receive the mock.
Call-server mode
Choose this in the full Network Rule editor. The interceptor makes the native request first, then replaces its response. A transport failure still fails. Header Rules can still affect the real outgoing call.

Each in-progress call keeps its rule settings. A later save affects subsequent calls. HEAD requests and statuses 204, 205, and 304 return no body. The rule still retains the body text that you entered.

Chrome's native Network panel shows actual network traffic. In call-server mode it can show the real server response while the page receives the mock. A bypassed call does not make a target network request. Workers, page navigation, and asset requests are outside this interception scope.
