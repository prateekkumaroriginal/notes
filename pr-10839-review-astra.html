Should I merge it now? Yes.

I found no blocking regression in the reviewed changes.

The route definitions retain their paths, guards and data. Component logic stays the same. The compiled templates retain their used dependencies, and both migrated entries stop loading SharedModule. The smaller bundles are measurable.

This recommendation applies to e92a285200. It is a code and build review. The logged-in browser checks below are the author's evidence, not checks I reran.

What changes

  • EditPreferenceModule and its routing module become EDIT_PREFERENCE_ROUTES. Its 48 declared components become standalone.
  • WhitelabelCoverPageModule and its routing module become WHITELABEL_COVER_PAGE_ROUTES. Its 25 declared components become standalone.
  • VipOfferShareModalComponent and ScrollContainerLoaderDirective become standalone too. SharedModule imports and still exports both.
  • Dashboard is the only remaining lazy application entry that loads SharedModule, down from three.

What I checked

Routes and component behavior

An AST comparison found 74 of the 82 changed files differ only in imports, standalone metadata or comments. The other eight contain route and module wiring, the DatePipe provider, or the removed HTML binding. No component method body changes.

The cover-page route array is unchanged after removing the NgModule wrapper and renaming the export. Edit-preference retains its route definitions; its nested cover-page lazy import now points at the route array. The app's parent guards and permission data remain in place.

Template dependencies

Fresh Angular compilation emits all 650 components present in the base output. Of those, 644 retain exactly the same matched directive and pipe dependencies. The other six lose only NativeElementInjectorDirective from ngx-intl-tel-input. None of those six templates contains a phone input.

The six are GroupBadgesComponent, BlockUsersComponent, PreviewCreatorBioComponent, VipOfferShareModalComponent, AddMarketingPageSectionComponent and AddSectionLayoutPickerModalComponent.

Providers remain available

DelegateDetailsComponent now provides DatePipe, and its transaction-detail modal remains a child in its template. DatePipe is also already in the shared root provider list registered by AppModule. The provider move does not leave either component without it.

AppModule provides TitleCasePipe, and NgxImageCompressService declares providedIn: 'root'. Removing their EditPreferenceModule registrations does not remove access to them. SharedModule's provider list and all 160 exports are unchanged.

The removed social binding was invalid

The PR removes [socialHandles]="socialHandles" from the social-links modal. That component has no socialHandles input. Its existing subscription reads saved handles from LinkInBioDataService, so this deletion does not remove the actual data path. The old CUSTOM_ELEMENTS_SCHEMA had hidden the invalid binding.

One minor cleanup

git diff --check reports trailing whitespace at line 8 of pending-request-popup.component.ts. Remove it when convenient. It is not a reason to hold the merge.

Independent bundle measurements

Initial JavaScript falls by 4 bytes, from 7,140,936 to 7,140,932 bytes. SharedModule appears in the static dependency graph of 1 of 45 lazy application entries. Those entries include dynamically loaded components as well as routes.

I calculated these values from Angular's build statistics, followed static JavaScript imports and subtracted the initial main, polyfills and scripts chunks. These are bundle sizes, not compressed transfer sizes or loading times.
