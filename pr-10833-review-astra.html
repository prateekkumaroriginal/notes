Wallet becomes standalone and stops loading SharedModule.

Reviewed 24 September 2026 · Head 9f85284bbcb · Base f26da3be4d5 · 53 changed files

Pull request · Implementation notes · Checks run · Before release

No new defect found

I found no actionable regression in the reviewed diff. The route structure survives the migration, the compiled template dependencies match apart from one unused phone-library directive, and both base and head pass the TopFans QA build.

The lazy-load reduction holds up in an independent build. Wallet needs 2,370,199 fewer bytes of JavaScript beyond the initial load, a 58.5% reduction. This is a useful change.

This review does not verify signed-in payment, refund, payout, or fulfillment actions. Those flows still need the checks below before release.

What changed

The app now lazy-loads WALLET_ROUTES instead of WalletModule. The PR removes the wallet routing and feature modules, converts their 35 declared components, and makes eight shared components, directives, and pipes standalone. Referrals is one of the 35 former declarations, though its file lives under Monetize.

Each converted component imports what its template uses. Table and resend verification also replace their SharedModule imports with direct dependencies. Those shared consumers matter because a remaining static import would keep pulling the large module into wallet.

Insights imports TransactionHistoryComponent directly. Its parent route now provides WalletHomeService, which the nested refund modals inject.

The checks that mattered

Routes and permissions stay intact

I parsed the old and new route definitions and compared the old routes with the new wrapper's children. All 26 route records match, including component names, redirects, guards, permission data, nested purchase routes, and the wildcard fallback.

The new empty-path wrapper puts WalletHomeService above both wallet branches. The outer app route still carries the authentication, permission, and creator-approval guards. Wallet remains lazy-loaded at the feature boundary.

Wallet routes · App route and guards

The refund modals retain their service

Transaction history renders transaction details, which can render the refund actions and their accept and reject modals. Those modals inject WalletHomeService. The new provider on the Insights parent route covers this chain when the earnings screen uses transaction history.

I checked the source dependency chain. I did not submit a refund or instantiate these screens with an authenticated account.

Insights provider · Refund modal templates

Template imports match the base

I compiled base and head separately with Angular's compiler, then compared the matched directive and pipe dependencies for all 656 components. The sets match for 652 components. No component gains a matched dependency.

The four differences are connect credit card, current balance, payout account section, and transaction history. Each loses only NativeElementInjectorDirective from ngx-intl-tel-input.

That directive attaches the host element to an Angular form control's nativeElement property. The four templates do not use the phone input widget, and the application search found no consumer of that added control property. I do not consider its removal a defect.

This comparison matters because the repository has strictTemplates: false. A build can succeed even when a plain directive attribute no longer matches an imported directive.

Removed module providers have replacements

The app's shared root providers already supply DatePipe and the circle-progress configuration. Wallet no longer needs its own copies. I also checked wallet templates for mask bindings before accepting the removal of provideNgxMask().

The eight shared declarations move into SharedModule's imports and remain exported, so existing NgModule consumers can still use them.
