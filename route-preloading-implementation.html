Route code preloading in TopFans

TopFans downloads a destination's lazy JavaScript before the user clicks. Visible navigation links preload during idle time. Tabs, forms and content cards usually wait for hover, keyboard focus or a press.

Navigation still runs through the existing router and click handlers. The preloader does not call the destination's APIs or run its guards and resolvers.

What the preloader loads

Route code preloading uses RoutePreloadService and appPreloadRoute to import a destination's lazy JavaScript ahead of navigation.

The implementation reuses Angular's route configuration and the existing intersection-observer directive. It adds no package. The destination still fetches its data through the normal page flow.

What happens before a click

  1. PreloadRouteDirective receives a visibility or intent event.
  2. It gets a URL from an explicit string, a URL function and its argument, or the host element's RouterLink.urlTree. An empty result can fall back to the router link. With neither source, it does nothing.
  3. RoutePreloadService checks the browser platform, the URL's started state and the network hints.
  4. A view trigger queues work for idle time. An intent trigger starts immediately and cancels queued view work for that URL.
  5. The service parses the primary-outlet path, finds a route, imports its lazy code and follows matching child routes.

The directive listens to mouseenter, focusin and pointerdown. Pointer down covers a mouse press, touch and pen. It starts work before the click handler runs, but a phone tap may leave too little time to finish a large download.

View detection comes from IntersectionObserverDirective. It uses a 0.5 threshold and an initial viewport check. Setting preloadOnView to false disables the view trigger while retaining intent events.

Scheduling, network rules and repeat calls

RuleCurrent behavior
ViewrequestIdleCallback with a 2,000 ms timeout. Fallback to setTimeout after 200 ms.
IntentStart immediately. Cancel queued view work for the same URL.
Constrained connectionSkip when navigator.connection.saveData is true or effectiveType is slow-2g or 2g. Browsers without these hints continue normally.
Repeat URLA service-level set tracks the exact URL string for the life of the app. A rejected asynchronous load removes it so another trigger can retry.
Different URLs, same codeThe service can visit the loader again. JavaScript module caching normally avoids another download of the same imported chunk. This is not a chunk-keyed queue.
Server renderThe service returns before browser work. The existing observer guards its browser APIs with cs.isBrowser.

The URL function runs in the directive before the service checks whether loading is necessary. It can run again on later intent events. The saved cost is URL construction during change detection, not a promise that each builder runs once.

Three ways to provide a target

Read the existing router link

The attribute alone uses the link's resolved URL. This is suitable for visible navigation that users often open.

<a appPreloadRoute [routerLink]="['/wallet']">Wallet</a>

Keep a click handler and provide a URL

Use an explicit target when the handler must close a modal, check state or perform other work. Intent-only loading suits create forms and less common actions. The preloader does not run the handler.

<button
  appPreloadRoute="/auth/creators-signup"
  [preloadOnView]="false"
  (click)="onRequirementContinue()"
>
  Continue
</button>

Build a URL when a trigger fires

Pass a stable arrow-function property and the item it needs. The directive calls the function on a preload trigger. Avoid calling the builder in the template binding, which would rebuild the URL on each check.

<div
  [appPreloadRoute]="postDetailPreloadUrl"
  [preloadRouteArg]="post"
  [preloadOnView]="false"
>
  <!-- Existing post-card content and click handling -->
</div>

The post-card builder checks the post key. Downloadables preload /dashboard. Other posts build the post-detail route and encode its dynamic segments. Constants and simple joins remain ordinary bindings.

These are shortened usage examples. The inventory contains the exact current opening tags.

How route targets match

The service walks the route configuration in order. An ordinary leaf route must consume every remaining URL segment. A route with children can consume a prefix, then continue into its child configuration. This lets a target such as /monetize/vip-offers/add-offer reach the add form's lazy loader.

Custom route.matcher functions handle their own matching, including case-insensitive marketing paths. Redirect entries and routes with canMatch are skipped. The service does not evaluate canActivate or resolvers.

The loader follows the primary outlet and expects lazy child loaders to return a route array, directly or through a default export. Redirect-only targets, named outlets and module-class loaders are outside its current support.

Where preloading is installed

The source snapshot contains 231 directive bindings in 87 HTML templates. That includes 12 reusable table-renderer positions. Another 19 table column configs provide URL functions. Each loop can render many elements, and some branches appear only for a specific role or viewport. These counts are source bindings, not unique pages, downloads or visible links.

Table support keeps the URL beside the action

A page can set preloadUrl beside a column's clickEvent. The shared table passes the row to the function only on intent. The table already uses OnPush change detection.

clickEvent: (trx) => {
  this.goToCreatorProfile(trx);
},
preloadUrl: (trx) =>
  trx?.receiver_details?.user_name
    ? '/' + trx.receiver_details.user_name
    : ''

The optional callback also works on supported row-action definitions. The current 19 populated definitions are columns. A column without the callback does not gain a target automatically.

Where preloading applies

  • A link or component needs appPreloadRoute to start this preloader. Navigation from a service does not automatically get an intent trigger.
  • History-based back buttons, logout, query-only URL changes and page-load or API-response redirects do not get speculative downloads from this implementation.
  • Hashtag links inside post text and the home page's course clicks have no preload binding.
  • Owner-only Edit post links preload Dashboard, which may already have loaded through New post.
  • The live-stream opener preloads Dashboard. Other modal destinations may still need their own code when selected.
  • Authenticated visibility, permission checks, data fetching and click-handler side effects follow the existing application flow.
