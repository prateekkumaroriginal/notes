Useful improvements for Overidify

Start with reliable saves and safer request headers. Then help users understand which Rule applies. These changes will make daily development easier before we add more mock response options.

Prepared 2 November 2026Based on the source review from 1 November

What the extension already does

Overidify changes request headers and returns mock API responses. It already supports capture from DevTools, Rule copies, search, import, and export. Saved changes affect later requests. A request that has started keeps its original settings.

The distinction between a website and its API matters:

Website scope
The website domains where a Rule can apply. This uses the top-level URL in the address bar.
Request target
The outgoing API URL and HTTP method. A website can call an API on another host.
Header Rule
A Rule that supplies one set of request headers.
Switch Rule
A Rule with named header options. The selected option supplies the headers.
Network Rule
A Rule that returns a mock response for a request target within a website scope.
Activation
The step that applies saved Rules to browser requests. A successful save does not prove that activation succeeded.

The review evidence separates observed behavior, dependency advisories, and proposals. Performance improvements below still need measurements.

Fix saves and protect sensitive data first

Keep a saved Rule when activation fails

Ordinary editor saves write the Rule to storage before they check activation. If activation fails, the editor reports an error. A new Rule gets a fresh ID on each save attempt. A second attempt can therefore create a Rule copy by accident.

Keep one ID for each new draft. Show Saved and Activation pending as separate states. Offer Retry activation without another storage write. Import and duplication already separate these outcomes.

Check that repeated activation failures preserve one saved Rule. Also check that a storage failure creates no Rule. Source: save and activation, editor save handlers.

Choose which API hosts receive request headers

A Header Rule for localhost:4200 currently changes supported requests from that website, including requests to other hosts. An authorization token can reach a third-party service if that request also receives the header.

Add an optional destination restriction such as api.example.com. Show the website scope and allowed API hosts before saving. Keep the current shared website matcher for Header Rules, Switch Rules, Network Rules, and the popup.

This adds a safety control to the existing behavior. It is not evidence of a reported token leak. Source: request header conditions.

Update development dependencies with known advisories

The full dependency audit flags development tools, including Vite and the Rollup version used by CRXJS. Review the affected versions and their use, then update the tools and lockfile. Run the build and extension tests after the update.

Add dependency scanning to CI. Review each finding before using a forced dependency override. The Vite advisory and Rollup advisory describe specific attack conditions. These findings alone do not prove that the installed extension is exposed.

Limit the mock configuration sent to a page

The page bridge receives matching Network Rules, including disabled Rules and their response bodies. Send only enabled Rules and the fields needed to return the mock response. Do not include Rule names or other editor data without a runtime need.

Restrict local extension storage to trusted extension contexts where possible. Keep sensitive header values in the extension. Code that runs inside the website must not be treated as private storage. See Chrome's content script guidance.

Make Rules easier to understand and use

Show why a Rule applies

Add a Rule tester. The user enters a website URL, request URL, and method. Show which Rules match, which Network Rule wins, and which headers replace other values.

Use specific explanations such as Query parameter differs or A later Rule has higher priority. Reuse the application's matchers so the tester and live requests make the same decision. Later, add recent request activity with a clear distinction between the native Network response and the mock response received by the page.

Switch a complete test scenario in one action

A test scenario would be a saved choice of enabled Rules and selected Switch Rule options. For example, "Expired session" could select an account header option and enable the Network Rules that return authentication errors.

Let the user activate one scenario from the popup. Show the intended changes first. Apply the saved choices together, then report activation separately. This is the strongest larger feature after the reliability fixes.

Protect unfinished edits

Escape currently leaves an editor without checking for unsaved changes. Add a warning before a user leaves a changed form. Keep a recoverable draft for long response edits.

If another options tab changes the same Rule, tell the user before an older form overwrites it. Offer a way to review the newer saved Rule and keep the local draft.

Make Rule exports safe to share

A Rule export contains the exact saved header values and response bodies. Add a sharing review that identifies sensitive headers and lets the user remove or replace their values.

Support placeholders such as {{API_TOKEN}} for shared Rules. Keep an exact Full backup available as a separate choice. Imported placeholders must stay inactive until the user supplies the required values.

Cover more API test cases

Allow controlled request target patterns

Exact matching becomes difficult when requests contain timestamps, page numbers, or generated IDs. Add explicit options to ignore selected query parameters and match a path pattern. Keep exact matching as the default.

Later, add conditions for request bodies and GraphQL operation names. That would let two operations on the same endpoint use different Network Rules. Extend request target matching without changing the shared website scope logic.

Return delayed responses, failures, and sequences

Add a response delay to test loading states. Add a transport failure to test connection error handling. Keep this separate from an HTTP error response such as status 500.

A response sequence could return two errors, then a success. Named response variants could switch between populated data, empty data, and a validation error. Define when a sequence resets and whether each tab has its own sequence.

Handle large responses and long sessions

Check storage before opening a captured response

DevTools can retain a response body that is too large for the session storage used to open its draft. Several abandoned drafts can also fill that shared storage. Capture success does not guarantee that the editor can open the response.

Check available space before the handoff. Show an action the user can take if the body will not fit. Remove expired drafts and use storage suited to larger bodies if large captures remain a supported use case. Add similar checks before saving Rules. See Chrome's storage limits.

Keep capture and interception work bounded

The DevTools list keeps request rows without a fixed count limit. It sorts the retained history when it publishes changes and renders every visible row. Batch capture updates, render only the rows in view, and offer a history retention setting.

Measure request matching with many Rules. If it is costly, prepare URL match keys when settings change. Also measure the frame scans triggered by DOM additions. Use those results to limit repeated scans. These are optimization candidates; the review did not measure a performance regression.

Reduce friction in the popup and editors

  • Add Pause all Rules for this website, with a visible resume action and an optional expiry.
  • Create a Rule from the popup with the current website scope filled in.
  • Open a matching Rule's editor directly from the popup.
  • Add explicit priority controls and warnings when enabled Rules compete.
  • Show active, disabled, needs reload, and activation failed states. Offer a reload action for affected tabs.
  • Rename the Header Rule editor's "Domain" field to "Website domain". Explain its effect on requests to other hosts beside the field.
  • Add a compact list view, grouping by website, and an enabled-only filter.
  • Offer light and system themes as application options.
  • Add response templates for empty results, pagination, validation errors, and authentication failures.

Suggested order of work

  1. Fix save and activation outcomes. Review the dependency advisories. Add destination restrictions for sensitive headers.
  2. Build the Rule tester. Add unsaved-change protection and storage checks.
  3. Add test scenarios, flexible request targets, and more mock response behavior.
  4. Measure long-session costs. Use the results to select performance work.

Keep regression tests for matching decisions, state changes, failure handling, and side effects. Check layout and routine UI wiring during implementation. Keep one-time screenshots and scripts outside the retained regression suite.

What the review checked

The review inspected the README, behavior docs, storage code, matchers, background workers, page bridge, editors, popup, and DevTools capture code at commit 20d17b0.

  • All 120 automated tests passed during the 1 November review.
  • The production dependency audit reported no known advisories at that time.
  • The full audit reported development dependency advisories. Each requires a review of affected versions and attack conditions.
  • The save retry behavior and storage mismatch came from code inspection and documented browser limits.
  • The review did not include a visual check of the running extension, a performance benchmark, or an exploit test.

This document proposes work. It does not report that these application changes have been made. Its terminology follows the project's Rule definitions and Network Rules glossary.
