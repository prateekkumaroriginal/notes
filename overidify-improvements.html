What to improve in Overidify

01Make Save dependable

A Rule can be saved but fail to activate. Clicking Save again can then create a second Rule.

Show saved and active states separately. A repeated Save should update the same Rule. Let the user retry activation without saving another copy.

For example, show "Rule saved. Activation failed" with a Retry activation action.

02Explain which Rule applies

When a mock does not appear, users have to guess whether the website, request URL, method, or priority caused it.

Add a Rule tester. Enter the website URL, request URL, and method. Show matching Rules, the winner, and the reason each other Rule does not apply.

For example, "The query parameter differs" or "A later Rule has higher priority."

03Switch a whole test setup

A test case can need several Rules and a particular Switch Rule option. Changing them one at a time is slow and easy to get wrong.

Add named test scenarios. One action selects the required header options and enables the right Network Rules together.

For example, "Expired session" selects the test account and enables its authentication error responses.

04Choose which API hosts receive headers

A Header Rule for a website currently affects supported requests to other hosts too. Sensitive headers can reach destinations the user did not intend.

Add an optional list of allowed API hosts. Show both the website scope and the request destinations before saving.

For example, add a test token to requests from localhost:4200 only when they go to api.example.com.

05Protect unfinished edits

Leaving an editor can discard unsaved changes. A second options tab can also change the same Rule while an older form is still open.

Warn before leaving a changed form and keep a recoverable draft. Before saving, flag newer changes to the same Rule so the user can review them.

For example, reopening the editor restores an unfinished response body instead of starting over.

06Make request targets more flexible

Exact URLs are awkward when requests contain timestamps, page numbers, or generated IDs. Different GraphQL operations can also share one URL.

Allow users to ignore selected query parameters and match path patterns. Add request-body and GraphQL operation conditions later. Keep exact matching as the default.

For example, match /users/123 and /users/456 with one path pattern while still requiring the correct method.

07Test delays, failures, and retries

A fixed response does not cover loading states, connection failures, or recovery after several failed requests.

Add response delays, transport failures, and response sequences. Keep a connection failure separate from an HTTP error response.

For example, return two errors followed by a success to check the app's retry behavior.

08Make Rule exports safe to share

A Rule export contains exact header values and response bodies. Sharing it can also share test tokens or private response data.

Add a review that lets users remove sensitive values and replace tokens with placeholders. Keep an exact Full backup available as a separate choice.

For example, export {{API_TOKEN}} instead of a token. Keep the imported Rule inactive until the recipient supplies its value.

09Handle large captured responses

DevTools can retain a response that will not fit in the session storage used to open its draft. Abandoned drafts also use that space.

Check available storage before opening the editor. Remove expired drafts and give the user a useful action when a response will not fit.

For example, explain that draft storage is full and offer to clear old drafts before trying again.

10Do more from the popup

Small tasks such as finding a Rule's editor or pausing several Rules require extra navigation and individual toggles.

Add actions to pause all Rules for the current website, open a Rule's editor, and create a Rule with the website already filled in. Offer a reload action when activation needs it.

For example, pause every matching Rule to compare the app's real behavior, then resume them in one action.

11Make large Rule collections easier to scan

A long list of cards makes it harder to find active Rules, compare priorities, and see which website each Rule affects.

Offer a compact list, website groups, an enabled-only filter, and explicit priority controls. Add light and system themes for users who prefer them.

For example, filter to enabled Rules for one website and change their priority without opening each editor.

12Keep long DevTools sessions responsive

Capture histories grow without a fixed request-count limit. Sorting and rendering the retained rows can add work as a session grows.

Measure long sessions, then batch capture updates, render only visible request rows, and offer a history retention setting. Also measure matching with many Rules and repeated frame scans.

For example, keep the full retained history searchable while rendering only the rows currently in view.

13Update development tools with known advisories

The dependency audit flagged development tools, including Vite and the Rollup version used by CRXJS. These findings need a review of affected versions and attack conditions.

Update the affected tools and lockfile, then check the build and extension behavior. Add dependency scanning to CI so new advisories are visible.

14Send less mock configuration to pages

The page bridge receives matching Network Rules, including disabled Rules and their response bodies. This exposes configuration that the page does not need to use.

Send only enabled Rules and the fields needed to return a mock response. Keep editor data and sensitive header values in the extension.

For example, a disabled Network Rule's response body should stay in the extension until the Rule is enabled.
